## APIエンドポイント
### 方針
- MVPリリース：既存のアプリ使用(HTTP Request Shortcuts)
- 本リリース：MVPで評判が良ければ設定が簡単なアプリの作成を検討
　　　　　　　アプリを作成するならWebサイトをウィジェットとして表示できるアプリがいいかも
### 開発環境でのテスト
■作業内容
- API用のエンドポイントを作成
  app/controllers/api/mood_records_controller.rb
- UserテーブルにAPIトークン追加
  どのユーザーの通信か判別するため
■エラー解決
- 接続するIPアドレスがはじかれる
  エラー：Cannot render console from 172.18.0.1! Allowed networks:～
  対策：config/environments/development.rb　に下記を追加
  　　　config.web_console.allowed_ips = '0.0.0.0/0'　
- ログインしていないのでログイン画面に遷移する
  対策：一時的処置として、API用のコントローラーはログインをスキップした
  　　　本番環境ではこれでセキュリティが担保できるか確認する
### セキュリティ性の担保
- 何を知りたい
  - 通信の安全性の確保ができているか
    ・アカウントを持つAPIトークンを発行されたユーザーのみ通信ができること
    ・ログイン関係なしに通信できてもいいか
  - 悪意のあるリクエスト発信の際に問題にならないか
    ・相手はアカウントを保持していて、リクエストの信頼性確認では対応できない
    ・アクションを起こさせないことやデータをテーブルに保存させないことが大事
- 調査(全体的な安全性)
  - Railsのデフォルト機能で守られているので基本は意識せずにOK
- 調査(通信の安全性)
  - 調査結果
    ・名称：APIリクエスト　←外部アプリからのリクエストの呼び方
    ・処理の流れ：ブラウザが送信するリクエストと同じ
  - 対策(MVPリリース)
    ・APIトークン認証
      ハュシュ化・最低32文字の長さ・再発行可能
    ・HTTPSの必須化
      「config.force_ssl = true」が設定されているか確認
    ・ログ
    　認証失敗のログ・異常なアクセスパターン・トークンの再発行履歴
  - 対策(問題が起きれば設定)
    ・レート制限
      1日に1個の気分しか記録できないのでそんな暇なことをするのかが不明
  - 対策不要
    ・CSRFの解除
      逆にこちらが流出した場合、アカウントを乗っ取れるので表示させる方が危険と考える
    ・CORSの設定
      基本的にはWebサイトへの制限なのでアプリに対しては意味がない
- 調査(悪意のあるリクエスト)
  - トークン認証を通過したデータの対策
    ・SQLインジェクション対策
      ➡ストロングパラメータを受け取っているのでOK
    ・ストロングパラメータ
      ➡設定している
    ・バリデーション
      ➡設定する
    ・スコープの制限
  - 自分の認識
    自分が未知の設定は出てこなかった。
